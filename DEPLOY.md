# Shipping Swipe4Change without a machine of your own

The app is three separate things. Nothing here needs your laptop to stay on.

| Piece | Runs on | Cost |
| --- | --- | --- |
| Database (`users`, `petitions`, `signatures`, …) | Supabase | Free tier |
| API (`backend/server.js`) | Render | Free tier (sleeps when idle) |
| The app itself | Firebase Hosting (web) and/or EAS Build (iOS/Android) | Free / $99 a year for the App Store |
| Sign-in | Firebase Auth | Free tier |

Do the steps in order — each one produces a value the next one needs.

---

## 1. Database — Supabase

1. Create a project at [supabase.com](https://supabase.com). Save the database password somewhere safe.
2. Open **SQL Editor → New query**, paste the entire contents of [backend/schema.sql](backend/schema.sql), and run it. It creates all six tables and turns on row-level security.
3. Go to **Project Settings → API** and copy two values:
   - **Project URL** → this is `SUPABASE_URL`
   - **`service_role` secret** → this is `SUPABASE_SERVICE_ROLE_KEY`

> The `service_role` key bypasses every access rule in the database. It goes into Render and nowhere else — never into `.env` values prefixed `EXPO_PUBLIC_`, never into the app, never into git.

Until this step is done the API falls back to a JSON file on disk. On Render that file is wiped on every restart, so **Supabase is what makes the data real.**

---

## 2. Sign-in — Firebase

1. Create a project at [console.firebase.google.com](https://console.firebase.google.com).
2. **Build → Authentication → Get started → Email/Password → Enable.**
3. **Project settings → Your apps → Web (`</>`)** and register an app. Copy the six values from the `firebaseConfig` block into `.env`:

```
EXPO_PUBLIC_FIREBASE_API_KEY=
EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN=
EXPO_PUBLIC_FIREBASE_PROJECT_ID=
EXPO_PUBLIC_FIREBASE_STORAGE_BUCKET=
EXPO_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=
EXPO_PUBLIC_FIREBASE_APP_ID=
```

These six are *meant* to be public — they identify the project, they don't grant access. Access is controlled by the Authentication settings above.

Skip this and the app still runs, but accounts live only in the phone's local storage: no shared login, no account on a second device.

---

## 3. API — Render

The blueprint is already written: [render.yaml](render.yaml).

1. Push this repo to GitHub (see *Before any of this* at the bottom — nothing is committed yet).
2. At [render.com](https://render.com): **New → Blueprint**, pick the repo. Render reads `render.yaml` and proposes the `swipe4change-api` service.
3. Fill in the secrets it asks for. Only the first two matter for a working app:

   | Key | Value |
   | --- | --- |
   | `SUPABASE_URL` | from step 1 |
   | `SUPABASE_SERVICE_ROLE_KEY` | from step 1 |
   | `REGULATIONS_GOV_API_KEY` | free key at [api.data.gov/signup](https://api.data.gov/signup) — real federal comment periods in the feed |
   | `OPENROUTER_API_KEY` | optional — AI petition drafting |
   | `RESEND_API_KEY` | optional — emails abuse reports to you |
   | `ACTION_NETWORK_API_KEY` | optional — makes signatures real, not just rows in your database |
   | `OPENROUTER_SITE_URL` | your web URL from step 5, or leave blank |

   `ENCRYPTION_KEY` is generated by Render automatically. **Don't change it after users exist** — stored signatures are encrypted with it and won't decrypt with a new one.
4. Deploy, then confirm in a browser: `https://<your-service>.onrender.com/health` should answer `{"status":"healthy","database":"supabase"}`. If it says `"memory"`, the Supabase values didn't take.

**Free tier caveat:** the service sleeps after ~15 minutes idle and takes 30–60 seconds to wake. The first launch of the day feels broken. $7/month removes it; a cron ping every 10 minutes is the free workaround.

## 4. Point the app at the API

In `.env`:

```
EXPO_PUBLIC_API_BASE_URL=https://<your-service>.onrender.com
```

It is currently `http://192.168.86.250:3001` — your laptop's address on your home Wi-Fi. That address is exactly why the app needs local hosting today.

**This value is baked into the build, not read at runtime.** I verified it: the bundle I just exported contains the literal string `192.168.86.250`. Change `.env` → rebuild, or the old address ships.

## 5a. Ship the web app — Firebase Hosting

[firebase.json](firebase.json) is already pointed at `dist/`.

```bash
npm install -g firebase-tools && firebase login && firebase use --add
```

Then, any time you want to publish:

```bash
npm run deploy:firebase
```

That builds `dist/` and uploads it. You get `https://<project>.web.app`. I ran the build step just now — it exports cleanly, 9.6 MB, 2.34 MB of JavaScript.

Afterwards, tighten CORS on Render: set `CORS_ORIGIN` to `https://<project>.web.app` instead of `*`.

## 5b. Ship the real app — EAS Build

[eas.json](eas.json) is set up with three profiles. You need a free Expo account.

```bash
npm install -g eas-cli && eas login && eas init
```

**The environment-variable trap:** `.env` is gitignored, and EAS respects gitignore when it uploads your project. Your keys would silently vanish from the build. Put them in EAS instead, once:

```bash
eas env:create --environment production --name EXPO_PUBLIC_API_BASE_URL --value https://<your-service>.onrender.com
```

Repeat for each `EXPO_PUBLIC_*` key. Then:

```bash
eas build --platform android --profile preview
```

That returns a download link to an `.apk` — install it on any Android phone, no computer involved. This is the fastest way to hold the real thing.

For the stores:

```bash
eas build --platform all --profile production
```

- **Android:** Google Play, $25 once, usually live within a day or two.
- **iOS:** Apple Developer Program, $99 a year. You cannot put an app on an iPhone permanently without it.

Then `eas submit --platform android` / `--platform ios`.

After the first store release, most changes ship without a new build:

```bash
eas update --branch production
```

---

## Two things missing before a store submission

- **No app icon or splash image.** `assets/` holds only fonts, so builds get Expo's default icon. You need a 1024×1024 PNG icon and a splash image, wired into `app.json`.
- **Push notifications are local-only.** `expo-notifications` is installed and schedules local reminders; real server-sent push needs an EAS project id and the `push_token` column (already in the schema) actually populated.

## Before any of this

Nothing in this project is committed to git. Render and EAS both build from a repository, so a commit and a GitHub push are the true first step.

`.gitignore` already excludes `.env` — keep it that way. The `service_role` key and `ENCRYPTION_KEY` belong in Render's dashboard only.
